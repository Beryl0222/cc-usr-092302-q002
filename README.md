# 基层心血管影像联动与转诊服务

富平县医院影像中心为 24 家基层机构出具心电、心脏 CT、冠脉造影报告。本服务在既有事件信封
（`event_id / kind / occurred_at / subject_id / version`）之上，构建影像联动与跨院转诊的
领域内核：保存检查申请、设备与协议版本、影像索引、结构化判读、补充意见、风险分层、
转诊理由、接收机构、患者授权与回执，并保证责任链、版本顺序、最小披露与全程可还原。

## 设计原则

### 1. 四条责任链各自独立

| 责任链 | 允许模态 | 判读角色 | 临床签署角色 |
| --- | --- | --- | --- |
| 低危筛查 `LOW_RISK_SCREENING` | 心电、心脏CT | 影像专家 | 基层临床医生 |
| 无症状高危识别 `ASYMPTOMATIC_HIGH_RISK` | 心电、心脏CT、造影 | 影像专家 | 基层 / 接收临床医生 |
| 术前测量 `PREOPERATIVE_MEASUREMENT` | 心脏CT、造影 | 影像专家 | 接收机构临床医生 |
| CT-FFR 补充判断 `CT_FFR_ADJUNCT` | 心脏CT | 影像专家（解剖学判读）+ CT-FFR 分析者（附属分析） | 接收机构临床医生 |

**任何影像/分析意见都不能替代临床医生签署**：影像专家与 CT-FFR 分析者的角色永远不具备签署
资格（`chains.js` 中的 `assertCanSign` 是硬闸门）；CT-FFR 附属分析必须挂靠同次 CT 当前
有效的解剖学判读，二者成对出现，不能单独作为转诊依据。一次转诊只能包含同一条责任链、同
一位患者的检查。

### 2. 版本顺序：断网、重传与更正

- 事件存储只追加：每个流（`exam:*` / `referral:*`）的 `version` 按到达接受顺序单调递增；
  全局 `seq` 用于队列排序。
- **断网补传**：晚到事件正常获得新版本号，但保留原始 `occurred_at` 并打 `backfilled=true`，
  与 `recorded_at` 一起还原"何时发生、何时入库"；未声明补传而时间倒退的写入被拒绝。
- **重复上传**：相同 `event_id` 的重传幂等回放；相同内容校验和但换了 `event_id` 的文件
  按重复内容拒绝，不产生第二份影像。
- **专家更正**：不覆盖旧意见，追加新版本（`supersedes_version` 指向旧版），旧版永久留痕；
  只能更正其所属判读谱系的当前有效版本，不能签署已被取代的判读。

### 3. 危急信号只升级相关患者

`CRITICAL` 分层或危急信号只把**该患者**的检查在机构工作队列中置顶并标记
`CRITICAL_AWAITING_ACK`。队列结构上不存在冻结状态（`frozen:false`），其他患者的判读、
签署、转诊全程不受阻塞；升级范围也不跨机构。临床医生回执后升级解除，再次出现新信号可
再次升级。

### 4. 最小披露与授权生命周期

- 披露包 = **目的白名单 ∩ 患者授权类别**：低危随访不送影像索引；高危识别不搭车 CT-FFR；
  CT-FFR 包必须同时包含解剖学判读与附属分析。被更正的旧判读内容不跨院发送，只留版本指针；
  跨院身份字段仅 `patient_id`。
- 未经临床医生签署的检查不能发起转诊或披露。
- 撤回授权分三种情形：
  - **尚未用于诊疗**：转诊置为 `REVOKED`，停止共享，已披露资料由接收机构确认停止访问与
    处置（`SHARING_DISCONTINUED`），此后受理/预约/再披露全部被拒；
  - **已交接、病历未形成**：诊疗不中断但禁止任何后续披露，最终处置照常留痕；
  - **已进入病历**：决定不回退（保持 `CLOSED`），撤回本身作为可追溯留痕保存。

### 5. 预约必须与接收机构实际状态一致

接收机构目录带版本号，记录受理开关、号源占用、时间与联系人。预约要约盖目录版本戳；
患者确认前若机构任何状态变化，旧要约立即失效（患者视图返回 `STALE` 且不展示过期时间/
联系人，提示按最新通知重新确认）；已确认的预约直接核对该号源当前时间与联系人，其他号源
变动不影响它，机构暂停受理或改了该号源信息则立即提示失效。只有指定接收机构能受理、回执
交接和记录最终处置。

### 6. 一次转诊完整还原

`referralTimeline(referralId)` 合并检查流与转诊流，按业务时间（同刻按全局序号）排序，
可从一次转诊还原：申请 → 设备协议 → 影像（含断网补传标记）→ 判读谱系与补充意见 →
风险/危急 → 医生签署 → 授权 → 转诊理由与最小披露 → 受理 → 预约 → 交接回执 →
最终处置及病历定位号。

## 代码结构

```
contracts/event.schema.json   事件信封合同（基线字段 + 链路/版本扩展）
src/vocabulary.js             事件、目的、角色、风险、状态取值表
src/errors.js                 机器可读的领域错误码
src/envelope.js / contract.js 信封构造与基线最小校验
src/event-store.js            追加存储：版本单调、幂等、并发、补传语义
src/chains.js                 四条责任链策略表与签署闸门
src/projections.js            纯函数状态折叠（检查流 / 转诊流）
src/disclosure.js             最小必要资料类别与披露包裁剪
src/receiver-directory.js     接收机构号源/联系人目录与一致性校验
src/imaging-service.js        命令式应用服务（校验 -> 追加事件）
src/read-models.js            机构队列、患者预约视图、转诊摘要
tests/                        node:test，31+ 用例
```

## 本地检查

```bash
npm test      # 32 个用例：责任链、版本顺序、危急升级、授权撤回、披露裁剪、预约一致性、全链还原
npm run demo  # 富平场景：基层CT -> 断网补传 -> 专家更正 -> 危急升级 -> 转诊 -> 处置
```
